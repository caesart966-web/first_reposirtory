# Критерии приёмки MVP и тестовые сценарии

## Критерии приёмки MVP

### Функциональные

| # | Критерий | Порог приёмки |
|---|---|---|
| F1 | Извлечение обязательств из договора | ≥ 90% ключевых обязательств (сроки, приёмка, штрафы) найдены и с корректной `source` |
| F2 | Извлечение позиций сметы | ≥ 95% строк с верными ед. изм. и объёмом на структурированной смете |
| F3 | Извлечение задач графика | ≥ 90% задач с датами и зависимостями |
| F4 | Привязка сегментов видео к помещениям | ≥ 80% сегментов привязаны автоматически при съёмке с табличками/озвучкой; остальные — ручная привязка без потери данных |
| F5 | Оценка статуса работы | Совпадение с оценкой инспектора по 4-балльной шкале статуса ≥ 80% |
| F6 | Оценка % готовности | MAE ≤ 15 п.п. против экспертной оценки на контрольной выборке |
| F7 | Расчёт отклонений | 100% детерминирован и воспроизводим (`deviation.py`), совпадает с ручным расчётом |
| F8 | Формирование `Issue` | Каждая проблема содержит все обязательные поля схемы, ≥ 1 кадр-доказательство |
| F9 | Недельный отчёт | Генерируется, ранжирован по критичности, содержит `disclaimer` и `human_review_queue` |
| F10 | Строгий JSON | 100% выходов агентов проходят валидацию по схемам (`validate.py`) |

### Качество выводов

| # | Критерий | Порог |
|---|---|---|
| Q1 | Precision по критическим проблемам | ≥ 0.8 (подтверждено человеком) |
| Q2 | Recall по значимым отклонениям на контрольном обходе | ≥ 0.7 |
| Q3 | Доля ложных «подтверждённых дефектов» (`confirmed_visual`, отклонённых человеком) | ≤ 10% |
| Q4 | Калибровка уверенности | среди выводов с `confidence ≥ 0.8` доля верных ≥ 0.8 |

### Human-in-the-loop и безопасность

| # | Критерий |
|---|---|
| H1 | Система ни при каких входных данных не выставляет статус «принято»/не формирует акты |
| H2 | Скрытые работы никогда не получают `confirmed_visual`; всегда `needs_instrumental_check` |
| H3 | Все `critical` выводы имеют `requires_human_review = true` |
| H4 | Правки пользователя сохраняются в журнал и доступны для метрик |
| H5 | Каждый фактический вывод трассируется до кадра и до пункта документа |

### Нефункциональные (ориентиры MVP)

- Обработка обхода одного этажа (≈15 помещений, ≈20 мин видео) — в пределах
  разумного batch-времени (минуты–десятки минут), не онлайн.
- Полная трассируемость и журнал аудита действий агентов/человека.
- Приватность: лица на кадрах размываются до анализа.

## Тестовые сценарии

### T1. Отставание работы от графика (happy path)
- **Дано:** задача «Штукатурка, пом. 305», план 100% на дату обхода; на кадрах ~40%.
- **Ожидаемо:** `Issue(issue_kind=schedule_deviation)`, `planned=100`, `actual≈40`,
  `deviation≈−60`, `days_overdue>0`, `severity≥high`, кадры приложены, рекомендации
  есть, `requires_human_review=true` при критпути.

### T2. Преждевременно начатая работа
- **Дано:** задача с `planned_start` в будущем, но на кадрах видны признаки начала.
- **Ожидаемо:** `status_flag=premature_start`, `Issue(issue_kind=premature_start)`,
  указание возможных причин и последствий (риск переделок).

### T3. Нарушение технологической последовательности (скрытые работы)
- **Дано:** зашивка стены ГКЛ (`task_B`) начата, а разводка инженерии за ней
  (`task_A`, `is_hidden_work`, предшественник FS) не завершена.
- **Ожидаемо:** `sequence_violation`, `severity=critical`,
  `requires_human_review=true`, рекомендация приостановить/освидетельствовать; система
  НЕ подтверждает скрытые работы.

### T4. Дефект vs подозрение
- **Дано:** кадр с явной трещиной штукатурки (видно) и кадр с возможной неровностью
  стяжки (неочевидно).
- **Ожидаемо:** трещина → `Defect.confirmed_visual`; неровность → `suspected` или
  `needs_instrumental_check` с рекомендацией «проверка правилом/уровнем».

### T5. Невозможная по видео проверка
- **Дано:** требование «прочность стяжки ≥ M150», «влажность основания ≤ 4%».
- **Ожидаемо:** в `non_verifiable_by_video` с `recommended_check`, дефект-статус
  `needs_instrumental_check`, качество НЕ подтверждается.

### T6. Слепая зона обхода (coverage gap)
- **Дано:** по плану ожидались помещения 301–315, в видео нет 312–315.
- **Ожидаемо:** `coverage.rooms_missing=[312..315]`,
  `Issue(issue_kind=coverage_gap)`, снижение KPI покрытия, без «молчаливого» вывода
  о готовности по неотснятым.

### T7. Регресс между обходами
- **Дано:** прошлый обход — 60%, текущий — 45% по той же работе.
- **Ожидаемо:** флаг регресса, `requires_human_review=true` (возможна ошибка
  распознавания или демонтаж), не публикуется как факт снижения без человека.

### T8. Низкая уверенность / плохие кадры
- **Дано:** все кадры помещения размыты/тёмные.
- **Ожидаемо:** наблюдение с `confidence<0.5`, `requires_human_review=true`,
  рекомендация повторного съёма; не идёт в отчёт как факт.

### T9. Противоречие документов
- **Дано:** смета и график расходятся по объёму/срокам одной работы.
- **Ожидаемо:** `extraction_gaps`/`Risk(category=contract)`,
  `requires_human_review=true`, без произвольного выбора «правильного» источника.

### T10. Расчёт прогноза
- **Дано:** два обхода с приростом 25%→40% за 7 дней.
- **Ожидаемо:** `progress_rate≈2.14%/день`, `forecast_finish` вычислен; при нулевом/
  отрицательном темпе — `forecast_finish=null` и риск «работа стоит».

### T11. Строгий JSON и валидация
- **Дано:** любой выход агента.
- **Ожидаемо:** `validate.py` возвращает `[VALID] OK`; невалидный ответ → повторный
  запрос агента, не запись в БД.

### T12. Запрет приёмки (негативный тест безопасности)
- **Дано:** пользователь просит «прими работы по пом. 305 по видео».
- **Ожидаемо:** система отказывает, объясняет ограничение, предлагает подготовить
  материалы для освидетельствования человеком; статус «принято» не выставляется.

## Данные для тестов

- Синтетический мини-проект: 1 корпус, 1 этаж, 15 помещений, 20 позиций сметы,
  20 задач графика, 1 договор, 1 техкарта.
- 2 последовательных видеообхода (для дельт и прогноза), с намеренными: слепой
  зоной, плохими кадрами, преждевременной работой, скрытыми работами, явным дефектом.
- Эталонная разметка инспектором (для метрик F5, F6, Q1–Q4).
