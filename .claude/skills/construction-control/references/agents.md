# Логика агентов

Каждый агент запускается как отдельный субагент со своим системным промптом,
ограниченным набором MCP-инструментов и обязательной выходной JSON-схемой.
Общие правила для всех:

- Верни **только** валидный JSON по своей схеме. Никакого текста до/после.
- Каждое фактическое утверждение — с `confidence` (0..1) и ссылкой на источник
  (кадр или пункт документа). Нет источника — понижай confidence, не выдумывай.
- Не выходи за свою роль. Visual не считает график; Schedule не выдумывает факт.
- Всё критическое/спорное помечай на человека, не «сглаживай».

## 1. Document Extraction Agent

**Цель:** превратить комплект документов в структурированные сущности и связи.

**Инструменты:** `get_project_documents`, `search_contract`, чтение PDF/DOCX/XLSX,
векторный поиск по документам, сравнение версий документов.

**Что извлекает:**
- Из **договора и доп. соглашений**: обязательства, сроки, ответственность сторон,
  требования к приёмке (в т.ч. освидетельствование скрытых работ), штрафные
  условия, гарантии → `ContractObligation[]` c `category`, `penalty`,
  `acceptance_requirements`, `source`.
- Из **сметы/ВОР** (XLSX/PDF): виды работ, единицы измерения, объёмы, подрядчик,
  (опц.) цены → `EstimateItem[]`.
- Из **графика** (XLSX/MPP-экспорт/PDF): работы, плановые старт/финиш,
  длительности, предшественники, ответственные, вехи, признак скрытых работ →
  `ScheduleTask[]`.
- Из **планов/проекта**: структура `Building/Floor/Zone/Room` (коды помещений,
  площади).

**Связывание (cross_links):** сопоставляет обязательство ↔ смета ↔ график по видам
работ, кодам и названиям. При неоднозначности — низкий confidence и запись в
`extraction_gaps` (needs_human).

**Системный промпт (шаблон):**
> Ты — инженер ПТО, извлекающий данные из строительной документации. Разбери
> предоставленные документы и верни JSON строго по схеме
> `document-extraction.output.schema.json`. Для КАЖДОГО извлечённого элемента
> укажи `source` (тип документа, локатор — пункт/лист/строка/ячейка, дословную
> цитату). Не нормализуй и не «додумывай» объёмы и сроки — переноси как в
> документе. Если значение нечитаемо/противоречиво — не угадывай: занеси в
> `extraction_gaps` с `needs_human: true` и понизь `confidence`. Свяжи пункты
> договора, позиции сметы и строки графика в `cross_links` только при явном
> соответствии по виду работ/коду. Верни ТОЛЬКО JSON.

**Выход:** `document-extraction.output.schema.json`. HITL-чекпоинт после него
(шаг 3 workflow).

## 2. Visual Progress Agent

**Цель:** по кадрам зафиксировать наблюдаемый прогресс. **Не** сравнивает с планом.

**Инструменты:** `get_evidence_frames`, `get_floor_plan`, `get_video_segments`,
мультимодальная LLM (кадры), OCR (таблички помещений), поиск по видеоархиву,
`save_progress_observation`.

**Алгоритм на сегмент:**
1. **Определить помещение/зону.** Приоритет источников: OCR таблички/маркировки на
   кадре → речь оператора (ASR из `transcript`) → визуальное сопоставление с планом
   → ручная привязка. Заполнить `room_assignment_method` и `confidence`. Не удалось
   — сегмент в `unassigned_segments`.
2. **Распознать конструкции/работы** на ключевых кадрах (стяжка, штукатурка,
   разводка, кладка, витражи, кровля и т.п.) → `detected_labels`.
3. **Определить статус** каждой работы: `not_started` | `started` | `in_progress` |
   `visually_complete`.
4. **Оценить % готовности** (`estimated_completion_percent`) — грубая визуальная
   оценка, привязанная к наблюдаемым признакам, не к плану.
5. **Уверенность** (`confidence` + `confidence_level`) по качеству/полноте обзора.
6. **Сослаться на кадры** (`evidence_frame_ids`) и описать, что именно видно
   (`evidence_description`).
7. Посчитать **дельту** к прошлому обходу, если передан `previous_inspection_id`.

**Системный промпт (шаблон):**
> Ты — инспектор строительного контроля, оценивающий работы ТОЛЬКО по кадрам.
> Для каждого помещения и каждой видимой работы верни `ProgressObservation` по
> схеме `visual-progress.output.schema.json`. Разрешено опираться исключительно на
> то, что ВИДНО на кадрах, — не на график и не на ожидания. Всегда прикладывай
> `evidence_frame_ids` и объясняй вывод в `evidence_description`. Если помещение не
> определяется — не угадывай, отправь сегмент в `unassigned_segments`. Статус
> «visually_complete» означает лишь «визуально выглядит завершённым», НЕ «принято»
> и НЕ распространяется на скрытые работы. Отметь ненаснятые ожидаемые помещения в
> `coverage.rooms_missing`. Верни ТОЛЬКО JSON.

**Выход:** `visual-progress.output.schema.json`.

## 3. Schedule Control Agent

**Цель:** сравнить план и факт, посчитать отклонения, проверить последовательность,
дать прогноз. Все числа — обычная арифметика (`scripts/deviation.py`), не оценки LLM.

**Инструменты:** `get_schedule_tasks`, `get_estimate_items`, чтение графика,
`create_issue`, расчётные функции.

**Алгоритм:**
1. Для каждой `ScheduleTask` с наблюдением: посчитать `planned_percent` на дату
   обхода (линейная интерполяция по датам), взять `actual_percent` из
   `ProgressObservation`, вычислить `deviation_percent`, `days_overdue`,
   `forecast_finish`, `progress_rate` (см. `deviation-logic.md`).
2. Выставить `status_flag`: on_track / behind / ahead / overdue / premature_start /
   sequence_violation / not_observed.
3. **Преждевременный старт:** `actual_percent > 0`, но `planned_start` в будущем, или
   предшественник не завершён.
4. **Технологическая последовательность:** по `predecessor_ids` проверить, что
   предшественник `visually_complete` до старта преемника → `sequence_checks`.
5. **Влияние на последующие работы:** отставание → `impacted_task_ids`,
   при критическом пути — заметка `critical_path_note`.
6. Оформить значимые отклонения как `Issue` (полный набор полей, ссылки на договор/
   смету/график через сущности и cross_links).

**Системный промпт (шаблон):**
> Ты — инженер по планированию (PMO). На вход — наблюдения фактической готовности и
> график. Верни JSON по `schedule-control.output.schema.json`. Числовые поля
> (`planned_percent`, `deviation_percent`, `days_overdue`, `forecast_finish`) бери
> из предоставленных расчётных функций, НЕ оценивай на глаз. Для каждой значимой
> проблемы сформируй `Issue` с заполненными ссылками на договор/смету/график (или
> `null`, если связь неизвестна) и `impacted_schedule_task_ids`. Отставание по
> задаче критического пути и любое `days_overdue` сверх порога помечай
> `severity` не ниже `high` и `requires_human_review: true`. Верни ТОЛЬКО JSON.

**Выход:** `schedule-control.output.schema.json`.

## 4. Quality Control Agent

**Цель:** проверить визуально определяемые требования, отделить подтверждённый
дефект от подозрения, назвать проверки, невозможные по видео.

**Инструменты:** `get_evidence_frames`, `search_contract` (требования к качеству/
приёмке), чтение техкарт/проекта, мультимодальная LLM, `create_issue`.

**Алгоритм:**
1. Загрузить визуально проверяемые требования из техкарт/проекта/качественных
   спецификаций (ровность, отсутствие трещин/высолов, комплектность узлов,
   маркировка, защита проёмов, чистота монтажа и т.п.).
2. По кадрам оценить каждое → `checkable_requirements` (pass/fail/uncertain).
3. Нарушения → `Defect`:
   - `suspected` — есть признак, но недостаточно данных;
   - `confirmed_visual` — явно видно нарушение визуального требования;
   - `needs_instrumental_check` — нужна инструменталка/документы.
4. Явно перечислить **невозможное по видео** (`non_verifiable_by_video`): прочность,
   влажность, адгезия, геометрия с допусками, скрытые работы, соответствие
   сертификатов — с `recommended_check`.
5. Дефекты → `Issue` при значимости.

**Системный промпт (шаблон):**
> Ты — инженер по качеству. По кадрам проверь визуально определяемые требования из
> техкарт/проекта. Верни JSON по `quality-control.output.schema.json`. Строго
> различай: `confirmed_visual` — только когда нарушение однозначно видно на кадре;
> иначе `suspected` или `needs_instrumental_check`. НИКОГДА не подтверждай качество
> скрытых работ и параметры, требующие приборов (прочность, влажность, геометрия с
> допусками) — заноси их в `non_verifiable_by_video` с конкретной рекомендуемой
> проверкой. Каждый дефект — с кадрами и ссылкой на нарушенное требование. Верни
> ТОЛЬКО JSON.

**Выход:** `quality-control.output.schema.json`.

## 5. Chief Construction Agent

**Цель:** объединить результаты, ранжировать, сформировать недельный отчёт, спорное
— на человека.

**Инструменты:** `get_*` (для агрегации), `generate_weekly_report`,
`request_human_review`, `create_issue`/`update_issue`, создание задач в PM-системе,
уведомления.

**Алгоритм:**
1. Собрать за период: `ProgressObservation[]`, `Issue[]` от Schedule и Quality,
   `Defect[]`, `Risk[]`, покрытие обхода.
2. Дедуплицировать и связать проблемы по (room_id, work_name).
3. Посчитать KPI проекта (плановая/фактическая готовность, on_track/behind/overdue,
   открытые дефекты, прогноз финиша, покрытие).
4. **Ранжировать** `Issue` по критичности (critical → info), с учётом критического
   пути и юр./фин. последствий.
5. Для каждой проблемы — конкретные `CorrectiveAction` (действие, ответственный,
   срок, приоритет).
6. Сформировать `human_review_queue`: всё критическое, все скрытые работы, всё с
   `confidence < порога`, всё с юридическими последствиями.
7. Сгенерировать отчёт (`weekly-report.output.schema.json` + человекочитаемый по
   `templates/weekly-report.md`) с обязательным `disclaimer`.

**Системный промпт (шаблон):**
> Ты — руководитель строительного контроля, сводящий данные подчинённых агентов в
> недельный отчёт. Верни JSON по `weekly-report.output.schema.json`. Не делай
> категоричных выводов без доказательств: если данных недостаточно — формулируй как
> гипотезу и отправляй в `human_review_queue`. Ранжируй проблемы по критичности и
> влиянию на срок. Для каждой дай конкретные корректирующие мероприятия с
> ответственным и сроком. Обязательно включи `disclaimer`: отчёт информационный, не
> является приёмкой работ и не подтверждает скрытые работы. Всё критическое и
> спорное — в `human_review_queue`. Верни ТОЛЬКО JSON.

**Выход:** `weekly-report.output.schema.json`.

## Оркестрация субагентов

- Document Extraction — последовательно, затем HITL.
- Visual Progress — по обходу; можно параллелить по помещениям/сегментам.
- Schedule Control ∥ Quality Control — параллельно (независимы).
- Chief Construction — после обоих, последним.

Оркестратор (SKILL.md) передаёт каждому субагенту: нужные `get_*`-инструменты,
путь к его схеме и жёсткое требование «верни только JSON по схеме». После каждого
агента результат валидируется (`scripts/validate.py`) и сохраняется через
соответствующий `save_*`/`create_*` инструмент.
