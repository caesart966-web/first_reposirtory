# Human-in-the-loop (участие человека)

Система — советующая, не решающая. Юридически и финансово значимые действия
остаются за специалистом. Этот контур встроен в модель данных (`review_status`),
в схемы (`requires_human_review`) и в инструмент `request_human_review`.

## Жёсткие запреты (никогда не автоматизируется)

Система **не**:
- подписывает и не формирует акты приёмки (КС-2, КС-3, АОСР, акты
  освидетельствования скрытых работ);
- подтверждает скрытые работы по видео (`ScheduleTask.is_hidden_work`);
- принимает работы окончательно (статус `visually_complete` ≠ «принято»);
- делает категоричных выводов без достаточных доказательств;
- меняет договорные/финансовые документы.

Эти правила закодированы:
- `generate_weekly_report` физически не выставляет статус «принято»;
- `Defect.defect_status = confirmed_visual` запрещён для скрытых работ и
  неинструментальных требований → только `needs_instrumental_check`;
- `issue.schema.json`: `severity = critical` ⇒ `requires_human_review = true`.

## Когда вывод обязан идти человеку (`requires_human_review = true`)

1. `severity = critical` (любой критический вывод).
2. Работа помечена `is_hidden_work` (скрытые работы).
3. `confidence < 0.5` (низкая уверенность).
4. Юридические/финансовые последствия: штрафы, срыв вехи договора, спор о приёмке.
5. Регресс готовности между обходами (стало меньше — возможна ошибка или демонтаж).
6. Противоречие между источниками (смета vs график vs факт).

Порог `confidence` для авто-принятия некритичных выводов конфигурируется
(по умолчанию `≥ 0.8` и `severity ∈ {low, info}` → `auto_accepted`).

## Точки участия в рабочем процессе

- **Чекпоинт A (шаг 3): проверка извлечённых данных.** После Document Extraction
  пользователь подтверждает/правит обязательства, объёмы, сроки, структуру
  помещений. Без подтверждения нельзя переходить к привязке (шаг 4).
- **Чекпоинт B (шаг 12): проверка выводов.** Перед недельным отчётом все элементы
  `human_review_queue` показываются специалисту.
- **Чекпоинт C (после отчёта):** отчёт помечен как информационный (`disclaimer`);
  превращение рекомендаций в задачи/уведомления — по решению пользователя.

## Действия пользователя над выводом

Через `update_issue` (или аналог для наблюдений/дефектов):

| Действие | `review_status` | Что происходит |
|---|---|---|
| Подтвердить | `confirmed` | вывод считается верным, идёт в отчёт как подтверждённый |
| Отклонить | `rejected` | вывод исключается из отчёта, помечается как ложное срабатывание |
| Исправить | `corrected` | сохраняются исходное и исправленное значения |
| Эскалировать | `escalated` | передаётся другому специалисту/на совещание |

## Сохранение правок для оценки качества системы

Каждая правка пишется в журнал обучающей обратной связи (не для дообучения сети на
1-м этапе, а для метрик и настройки порогов):

```json
{
  "entity_type": "Issue",
  "entity_id": "issue_a1",
  "field": "actual_percent",
  "system_value": 40,
  "human_value": 55,
  "action": "corrected",
  "actor": "инженер СК",
  "reason": "виден выполненный участок за перегородкой",
  "at": "2026-07-14T10:20:00Z"
}
```

Метрики, считаемые из журнала:
- **Precision по проблемам** = confirmed / (confirmed + rejected).
- **MAE процента готовности** = средняя |system_value − human_value| по `corrected`.
- **Доля выводов, ушедших на человека**, и доля из них подтверждённых — калибровка
  порогов `confidence` и `severity`.
- **Recall** — по контрольным обходам, где человек размечает всё (см.
  `acceptance-and-testing.md`).

Эти метрики — вход для настройки порогов и, в перспективе (не в MVP), для дообучения.

## Уведомления

`send_notification` уведомляет ответственных только после решения пользователя
(или по правилам эскалации для `critical`), чтобы система не рассылала
неподтверждённые обвинения подрядчикам.
