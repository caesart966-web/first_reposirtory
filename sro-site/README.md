# Сайт «Бизнес-Групп» — вступление в СРО

Одностраничный сайт (landing page) независимого эксперта, который помогает компаниям и ИП
вступить в СРО, подобрать и проверить СРО, подготовить документы, решить вопросы НРС и НОК
и получить сопровождение.

## Стек

- React 18 + TypeScript
- Vite 5
- Tailwind CSS 3
- lucide-react (иконки)
- Inter Variable (шрифт, локально через `@fontsource-variable/inter` — без внешних запросов)

Без роутера и без тяжёлых зависимостей. Фронтенд статический; единственная
серверная часть — обработчик заявок `public/api/submit.php` (см. «Заявки на
почту»), и она нужна только если сайт стоит на хостинге с PHP.

Графика двух родов: интерфейсные иконки и фоновые мотивы — SVG прямо в коде
(`components/icons.tsx`, `components/illustrations.tsx`), фотографии — WebP
с AVIF-дублем в `public/img/`.

## Запуск

```bash
cd sro-site
npm install
npm run dev        # http://localhost:5173
npm run build      # typecheck + прод-сборка в dist/
npm run preview    # локальный просмотр прод-сборки
```

Требование заказчика: форма обязана работать у посетителей из России **без
VPN и без задержек**. Это выполняет только контур со своим `submit.php`:
он лежит на том же домене, что и сайт, браузер посетителя никуда наружу не
ходит, письмо уходит сразу с хостинга. Web3Forms — зарубежный сервис и этому
требованию не соответствует; он остаётся только на время, пока у сайта нет
своего хостинга. Переезд на боевой контур — см. «Свой обработчик» ниже.

Контур проверен целиком 30.08.2026: настоящий проход квиза в браузере →
сборка с `VITE_LEAD_ENDPOINT=/api/submit.php` → PHP-сервер → письмо
(`SRO_MAIL_DRY_RUN`) с правильными получателем, темой и Reply-To.

Приёмников два, выбор зависит от того, где стоит сайт:

| Где стоит сайт | Приёмник | Почему так |
| --- | --- | --- |
| Российский хостинг с PHP | `public/api/submit.php` — свой обработчик на том же домене | **Рабочий вариант.** Web3Forms — зарубежный сервис, из России без VPN не открывается, и заявки не дошли бы |
| GitHub Pages, зарубежный хостинг | Web3Forms (значение по умолчанию) | PHP там не выполняется |

- В письме: тема `Заявка с сайта СРО — Имя, Телефон` (можно перезванивать
  прямо из списка писем), в теле — контакты и все ответы квиза.
- Кнопка «Ответить» в почте отвечает **клиенту**, а не сервису (поле `replyto`).
- Таймаут 10 секунд. Если сервис не ответил, посетитель видит «Не удалось
  отправить заявку», введённые данные сохраняются, есть кнопка «Попробовать
  снова» и прямые каналы связи. Молчаливого «успеха» не бывает.
- Форма защищена honeypot-полем: заполнившему его боту показывается обычный
  экран успеха, но заявка не отправляется.

Сменить приёмник можно без правки кода — через переменные окружения
(см. `.env.example`). Формат запроса и ответа у своего обработчика намеренно
такой же, как у Web3Forms, поэтому фронтенд одинаков для обоих:

```
# Свой хостинг с PHP:
VITE_LEAD_ENDPOINT=/api/submit.php
VITE_LEAD_ACCESS_KEY=<любая строка, та же что FORM_TOKEN в submit.php>

# Web3Forms:
VITE_LEAD_ENDPOINT=https://api.web3forms.com/submit
VITE_LEAD_ACCESS_KEY=<ключ сервиса>
```

Без этих переменных используются значения по умолчанию из `src/lib/lead.ts`.
В GitHub Actions они пробрасываются из Secrets репозитория, если заданы.

### Свой обработчик: что заполнить

`public/api/submit.php` попадает в сборку сам и оказывается по адресу
`/api/submit.php`. Перед заливкой на хостинг в нём заполняются четыре строки:

| Константа | Что вписать |
| --- | --- |
| `MAIL_TO` | куда приходят заявки |
| `MAIL_FROM` | **адрес на домене сайта**, например `zayavka@вашдомен.ru`. Заводится в панели хостинга. Чужой домен нельзя: не сойдётся SPF, и письма уйдут в спам |
| `FORM_TOKEN` | та же строка, что в `VITE_LEAD_ACCESS_KEY` при сборке. Если не совпадёт — сайт покажет экран ошибки |
| `ALLOWED_HOST` | домен сайта, чтобы чужая страница не слала заявки от вашего имени |

Обработчик отсекает заголовочные инъекции, ограничивает частоту (10 заявок
с одного адреса в час) и кодирует русскую тему письма по MIME.

Проверить его, не рассылая почту, можно так — письмо запишется в файл:

```bash
SRO_MAIL_DRY_RUN=/tmp/lead.eml php -S 127.0.0.1:8000 -t dist
curl -X POST http://127.0.0.1:8000/api/submit.php \
  -d '{"access_key":"<FORM_TOKEN>","message":"проверка"}'
cat /tmp/lead.eml
```

**Первое письмо почти наверняка попадёт в «Спам»** — это нормально для таких
сервисов. Нужно найти его, нажать «Не спам», добавить отправителя в адресную
книгу и сделать фильтр в папку «Заявки с сайта».

## Принципы контента

На сайте нет отзывов, выдуманных цифр, достижений, лицензий, цен и сроков —
только описание услуг и формата работы. Всё, что требует реальных данных,
вынесено в плейсхолдеры вида `[ИМЯ]`; пока плейсхолдер не заменён, блок с ним
не показывается, а не выводит скобки на экран.

Фотографий шесть. У пяти источник и лицензия подтверждены заказчиком; у шестой —
фона секции заявки — файл прислан заказчиком напрямую, а источник он пока не
назвал, и в учёте так и написано. Всё — в `public/img/CREDITS.md`. Логотипы СРО, НОСТРОЙ, НОПРИЗ, Минстроя, гербы и
флаги не ставятся: чужие обозначения плюс намёк на аккредитацию, которой нет.

Обещаний результата и сроков («вступление за 1 день», «гарантия внесения в
реестр», «ответ за 24 часа») на сайте нет и быть не должно: это не зависит от
исполнителя.

Единственное прямое обязательство — бесплатная консультация: она бесплатна
всегда, а не только в первый разговор. Это условие задал заказчик, в исходном
ТЗ его не было. Сказано оно в пяти местах — герой, «Стоимость» (подзаголовок
и карточка формата), FAQ, квиз, подвал; формулировки разные, смысл один.
Дословная оговорка «и первая, и все следующие» есть ровно одна, в подвале:
она переехала туда из убранной секции «Контакты». Меняете условие — правьте
все пять, иначе сайт начнёт противоречить сам себе.

## Ссылки мессенджеров и открытие приложения

Ссылки WhatsApp, Telegram и MAX открываются **в той же вкладке** — без
`target="_blank"`. Это не упущение, а условие работы: ни iOS, ни Chrome на
Android не запускают universal link / app link, если переход идёт в новую
вкладку. С `target="_blank"` нажатие на телефоне открывало пустую страницу
или веб-версию вместо приложения — заказчик поймал это на живом сайте.

Размен осознанный: на компьютере посетитель уходит на веб-версию мессенджера
и возвращается кнопкой «Назад». Цель лендинга — чтобы человек написал, а
телефонов среди посетителей заведомо больше. Телефон и почта всегда работали
так же, без новой вкладки.

Сторожит это `deeplinks.mjs`: проверяет, что ни на одной ссылке мессенджера
нет `target="_blank"` и что схема у всех `https` (у `tg://` нет universal
link — у кого нет приложения, увидит ошибку браузера). Проверено обратным
контролем: с возвращённым `target="_blank"` набор падает.

Мессенджеры на странице помечены атрибутом `data-channel` — раньше проверки
опознавали их как раз по `target="_blank"`, и признак пришлось заменить на
такой, который не завязан на поведение ссылки.

Две вещи, которые кодом не чинятся, если чат всё-таки не открывается:

- **Telegram.** Ссылка стоит на @username (`t.me/Igor_bgspb`), а не на номер.
  Форма `t.me/+<номер>` тоже рабочая, но открывает чат лишь у тех, кому
  владелец номера разрешил находить себя по телефону; у остальных приложение
  открывалось без чата. Заказчик поймал это вживую — с именем пользователя
  условия нет.
- **WhatsApp заблокирован в России.** Роскомнадзор исключил домены
  `whatsapp.com` и `web.whatsapp.com` из национальной системы доменных имён
  в феврале 2026 года; доступ то появляется, то пропадает, устойчиво работает
  только через VPN. Ссылка на сайте корректна, но у посетителя из России
  канал может не сработать — и это не чинится кодом. Решение, оставлять ли
  WhatsApp на сайте, за заказчиком; рабочие каналы для российской аудитории —
  Telegram, MAX и телефон.
- **Встроенный браузер мессенджера.** Если сайт открыт изнутри Telegram или
  VK, их встроенный браузер обрабатывает ссылки по-своему. Проверять нужно
  в обычном Chrome или Safari.

## Страницы видов СРО

Кроме главной у сайта три отдельные страницы — по одной на вид СРО:

| Адрес | О чём |
|---|---|
| `/sro-stroiteley/` | вступление в СРО строителей |
| `/sro-proektirovshchikov/` | вступление в СРО проектировщиков |
| `/sro-izyskateley/` | вступление в СРО изыскателей |

Попасть на них можно с главной: карточка вида СРО целиком кликается и ведёт
на свою страницу, кнопка «Подробнее» при наведении заливается фирменным цветом.

**Не одностраничник с роутером, а четыре обычных html.** Каждая страница —
своя точка входа Vite (`vite.config.ts`, `build.rollupOptions.input`). Так у
неё настоящий адрес: ссылку можно прислать, поисковик видит три отдельные
страницы, а хостингу не нужен фолбэк на `index.html`, без которого адрес,
открытый напрямую, отдавал бы 404.

**Что на страницах.** Кому обязательно членство, область деятельности, обе
таблицы взносов в компенсационные фонды, требования к специалистам, срок
рассмотрения заявления и — только у строителей — региональный принцип.
Содержимое лежит в `src/content/sroDetails.ts`.

**Ни одной цифры «на глаз».** Каждая величина на страницах — из закона, и
рядом с ней стоит статья, по которой её можно проверить. Суммы взносов —
это установленные законом МИНИМУМЫ: конкретная СРО не вправе взять меньше,
но своими документами может установить больше, и на странице это сказано
прямо. Про цены и сроки нашей работы там нет ни слова — таких данных
заказчик не давал.

**Глубина вложенности.** Пути к картинкам из `public/` и ссылки на секции
главной написаны руками, и на странице в подпапке они ломаются молча:
`./img/x.webp` превращается в `/sro-stroiteley/img/x.webp`, а `#services`
ведёт в никуда. Поэтому оба вида ссылок проходят через `src/lib/site.ts`, а
точка входа объявляет свою глубину один раз — `setSiteRoot('../')`. Сторожит
это набор `pages.mjs`: он открывает каждую страницу и требует, чтобы
картинки реально загрузились, а ссылки реально отвечали 200.

**Возврат в квиз.** Кнопка на странице ведёт на главную с уже выбранным
видом: `/?sro=construction#quiz`. Квиз читает параметр при старте и не
спрашивает про вид второй раз — человек уже ответил, открыв страницу.
Якорь при этом отрабатывает не сам: браузер прыгает к нему сразу после
разбора HTML, а разметку рисует React, и в этот момент секции ещё нет.
Прокрутку после отрисовки делает `src/lib/useHashScroll.ts`.

## Проверка цифр 04.09.2026 и почему таблиц взносов нет

Все нормы на страницах видов СРО прошли состязательную проверку: восемнадцать
утверждений, у каждого три независимых проверяющих с прямой задачей
**опровергнуть**, а не согласиться. Что она изменила:

| Было | Стало | Почему |
|---|---|---|
| изыскания — ч. 4 ст. 47 | **ч. 2 ст. 47** | ч. 4 к членству в СРО не относится |
| строители — ч. 2.1 ст. 52 как «обязанность» | **ч. 2 ст. 52** — обязанность, **ч. 2.1** — случай, когда членство НЕ нужно | порог сам по себе ничего не решает: сначала важно, с кем заключён договор |
| срок — ч. 5 ст. 55.6 | **ст. 55.6** без части | проверяющие разошлись: часть 4 или 5 |
| взносы — ч. 10–13 ст. 55.16 | **ст. 55.16** без части | порядок частей не подтверждён |
| снос — ст. 55.31 как «норма о сносе» | снос назван в области деятельности | ст. 55.31 — требования к сносу, а обязанность членства идёт из ст. 52 |
| «участвуете в 44-ФЗ и 223-ФЗ» | «**намерены** заключать договоры конкурентными способами» | взнос в КФ ОДО привязан к заявленному намерению, а не к факту участия |

**Правило, которое из этого следует: номер части статьи ставим только там, где
на нём сошлись все проверяющие.** Неверный номер части выглядит точнее, чем
есть, и подрывает доверие ко всей странице.

### Таблицы взносов: сняты и возвращены в тот же день

Проверка оставила два возражения:

1. **Первый уровень для строителей.** Три проверяющих с высокой уверенностью
   называют 60 млн ₽, а не 90 млн ₽. Значение 90 млн взято из уже сверенных
   данных соседнего проекта (`norma-site/src/config/facts.ts`) со ссылкой на
   435-ФЗ от 04.08.2023.
2. **Порядок частей ст. 55.16** — где строители, а где проектировщики.

Проверить по первоисточнику отсюда нельзя: правовые сайты закрыты сетевой
политикой — `consultant.ru`, `pravo.gov.ru`, `garant`, `cntd`, `sudact` дают
403 на CONNECT. Поэтому таблицы со страниц сняли: цифра, по которой человек
переводит деньги, не может стоять «примерно».

**В тот же день спор разрешился.** Заказчик прислал сохранённые страницы
работающего сайта конкурента по всем трём видам СРО. Все четыре таблицы там
совпали с нашими до рубля, включая спорный первый уровень 90 млн ₽. Итого
за 90 млн: наши данные, уже сверенные данные соседнего проекта и три живые
коммерческие страницы. Против — только память трёх проверяющих. Таблицы
возвращены, `FUNDS_CONFIRMED = true`.

Чего это не отменяет: сайт конкурента подтверждает, что так считает рынок,
но он не первоисточник. Перед выходом на боевой домен таблицы стоит сверить
с действующей редакцией ст. 55.16 ГрК РФ.

**Номера частей ст. 55.16 не проставлены и не будут** — проверяющие в них
разошлись, а страницами конкурента их не подтвердить: он частей не указывает
вовсе. Проверка `pages.mjs` отдельно следит, чтобы они не появились.

## Имя на сайте: компания, не человек

Сайт делался как страница частного специалиста и написан от первого лица.
03.09.2026 заказчик попросил убрать ФИО специалиста и представить компанию из
реквизитов — ООО «БИЗНЕС-ГРУПП». Сделано так:

- компания везде названа одинаково: **ООО «БИЗНЕС-ГРУПП»** (`CONTACTS.brand`),
  подпись под именем — «Вступление в СРО» (`CONTACTS.role`). Это шапка, подвал,
  `<title>`, описание и Open Graph;
- рядом с именем стоит ИНН там, где он к месту: в копирайте подвала и в
  карточке «Реквизиты» полным набором (ИНН, КПП, адрес), в политике и согласии
  — в определении Оператора (`REQUISITES` в `facts.ts`);
- ФИО на странице нет нигде, включая `<title>` и Open Graph;
- фраза «Меня зовут …» из блока «О специалисте» убрана, остальной текст
  первого лица оставлен: он читается как речь специалиста компании и держит
  главное обещание сайта — «работаете с одним человеком, а не с отделом
  продаж». В FAQ «частный специалист» заменён на «один специалист».

Сначала короткий бренд «Бизнес-Групп» стоял в шапке и подвале, а полное имя —
только в копирайте и документах. 03.09.2026 заказчик попросил единое написание:
разнобой читается посетителем как два разных лица, а имя из реестра — то, по
чему компанию проверяют. Длиннее короткого бренда на 6 символов, но помещается
в одну строку и на 1440, и на 360 — проверено на странице. Правило сторожит
набор проверок `naming.mjs`: он сверяет шапку, подвал, `<title>`, Open Graph
и описание, требует ИНН в подвале и запрещает короткое написание без «ООО»
и незаполненные реквизиты в квадратных скобках на экране.

Переводить весь текст на «мы» не стали: это 42 строки в 12 компонентах и
смена характера сайта, а не правка. Если заказчик решит, что компании нужно
«мы», — это отдельная задача.

Банковские реквизиты (счёт, БИК, корр. счёт) в репозиторий не внесены: они
для счетов и договоров, сайту не нужны.

## Подвал

Три колонки под общей капителью с разрядкой — той же, что у групп в «Услугах»,
чтобы подвал читался частью системы, а не тремя случайными списками. В
«Связаться» три яруса сверху вниз, от самого прямого канала к самому
отложенному: телефон крупно, почта, мессенджеры рядом плашек с подписями.
Ряду плашек нужно около 330px, поэтому правой части подвала отдано больше
ширины (2.4 против 0.9 у колонки бренда) и на планшете тоже проверено — одна
строка. В копирайте — юридическое имя и ИНН: по нему компанию можно проверить
в реестре, для подвала это дешёвый и честный знак «мы настоящие».

## Первый экран: кадр вместо портрета

Заказчик попросил первый экран «красивее и профессиональнее», но портрет
специалиста публиковать не будет. Экран двухколонный: текст слева, справа его
же фотография рабочего стола (каска, уровень, планы) в фирменном дуотоне на
подложке фирменного цвета со сдвигом — она даёт глубину вместо тени, которая
на светлом фоне читалась бы грязью.

Заголовок в колонке уже, чем был по центру, поэтому на `lg` его кегль 2.9rem
вместо 3.4rem — иначе ломался на пять строк.

Сначала этот же кадр стоял и фоном под квизом — как рамка страницы. Заказчик
заметил повтор; замена архивной синькой ему не понравилась. Сейчас под квизом
кадра нет: чистая тёмная заливка с двумя мягкими пятнами фирменного цвета.
Новый кадр заказчик присылает через репозиторий — скачать из интернета из этой
среды нельзя, фотостоки закрыты сетевой политикой (проверены pexels, unsplash,
pixabay, wikimedia, freepik). Как появится: `<picture>` на `opacity-50` плюс
плёнка `bg-accent-950/65`, контраст надписей перемерить (см. «Фон секции
заявки» ниже).

## Цвет

Акцент — кобальтовый синий (`accent` в `tailwind.config.js`), единственный
акцентный цвет сайта. Нейтральная шкала переопределена на тёплую: на чистом
сером холодный акцент и синие фотографии давали ощущение мороза. Это greige —
серый со сдвигом в жёлтый, а не бежевый, поэтому деловой вид сохраняется.

Фотографии подчиняются тому же правилу: тёмная точка дуотона — фирменный синий,
светлая — кремовая (см. `public/img/CREDITS.md`). Меняете одно — проверяйте
второе, иначе интерфейс и снимки разойдутся по температуре.

Фон секции заявки — фотография (каска «СРО», кодексы, чертежи), и она идёт
с затемняющей плёнкой поверх (`bg-accent-950/65` под кадром на `opacity-50`).
Плёнка не украшение: светлые места снимка поднимают яркость подложки под
белым заголовком и надписью «Заявка», а последняя — самая уязвимая, у неё
контраст ниже всех. Мерить надо по каждой надписи её собственным цветом, а не
по одному белому заголовку: у заголовка запас всегда большой, и замер по нему
разрешает то, что «Заявке» уже вредит. Замерено: без фото 8,56:1, с фото
и плёнкой 5,88:1 на десктопе и 6,07:1 на телефоне при норме 4,5; без плёнки
уходит ниже нормы. Меняете кадр — перемеряйте обе величины разом. Рисованный
вариант сцены со столом лежит в `assets-src/desk-drawing.svg`; рисунку плёнка,
наоборот, противопоказана — она съедает светлые линии.

Анимации лёгкие (fade/reveal/hover) и отключаются при `prefers-reduced-motion`.
Карточка приподнимается под курсором только если она кликается целиком:
подъём — это обещание клика (`src/components/ui/card.ts`).
