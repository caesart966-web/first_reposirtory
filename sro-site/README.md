# Сайт «Бизнес-Групп» — вступление в СРО

Одностраничный сайт (landing page) независимого эксперта, который помогает компаниям и ИП
вступить в СРО, подобрать и проверить СРО, подготовить документы, решить вопросы НРС и НОК
и получить сопровождение.

## Стек

- React 18 + TypeScript
- Vite 5
- Tailwind CSS 3
- lucide-react (иконки)
- Inter Variable (шрифт, локально через `@fontsource-variable/inter` — без внешних запросов)

Без роутера и без тяжёлых зависимостей. Фронтенд статический; единственная
серверная часть — обработчик заявок `public/api/submit.php` (см. «Заявки на
почту»), и она нужна только если сайт стоит на хостинге с PHP.

Графика двух родов: интерфейсные иконки и фоновые мотивы — SVG прямо в коде
(`components/icons.tsx`, `components/illustrations.tsx`), фотографии — WebP
с AVIF-дублем в `public/img/`.

## Запуск

```bash
cd sro-site
npm install
npm run dev        # http://localhost:5173
npm run build      # typecheck + прод-сборка в dist/
npm run preview    # локальный просмотр прод-сборки
```

## Карточка в мессенджерах и карта сайта

Две вещи, которых на самой странице не видно, но без которых сайт работает хуже.

**Картинка карточки (`og:image`).** Когда ссылку отправляют в WhatsApp, Telegram
или ВКонтакте, мессенджер показывает карточку: заголовок, описание и картинку.
Фотографии со страницы он для этого не берёт — ему нужно прямое указание,
и до 08.09.2026 его не было: карточка приходила без изображения.

Картинка одна на все одиннадцать страниц и собрана из фирменных элементов
сайта: знак весов из `illustrations.tsx`, тёмный фон `accent-950` как у блока
заявки и подвала, тот же Inter. Фотографии в ней нет намеренно — карточка
в переписке показывается размером с ноготь, и любой кадр там превращается
в кашу, а знак и имя читаются.

Генератор — `scripts/build-og.mjs`, кладёт `public/og.png` размером 1200×630
(этого размера ждут все мессенджеры). Playwright в зависимостях сайта нет:
картинка пересобирается редко, и тащить браузер в прод-сборку ради неё незачем,
поэтому модуль берётся из переменной окружения:

```bash
PLAYWRIGHT=/путь/к/node_modules/playwright-core/index.js node scripts/build-og.mjs
```

Шрифт вшивается в страницу из `node_modules`, а не тянется из сети: среда
сборки может быть без интернета, и тогда картинка молча уехала бы системным
шрифтом — на глаз почти незаметно, а фирменный вид уже не тот.

**Карта сайта (`public/sitemap.xml`).** Список всех адресов для Яндекса
и Google. Поисковик находит главную, но не обязан догадаться, что есть ещё три
страницы видов СРО и семь страниц услуг: ссылки на них лежат в выпадающем меню,
которое собирается скриптом. Карта называет все одиннадцать адресов прямо.

Список не пишется руками: `scripts/build-sitemap.mjs` собирает его из самих
файлов — каждая страница сайта это отдельный `index.html` со своей точкой входа
(см. `vite.config.ts`), появится новая — попадёт в карту сама. `lastmod`
намеренно нет: неверная дата хуже отсутствующей, а честную взять неоткуда.

**Домен подставляется одной командой.** Плейсхолдер `https://example.com` стоит
в тринадцати файлах: canonical, og:url и og:image одиннадцати страниц, карта
сайта и `robots.txt`. Пропустить одно место легко, а страница с чужим canonical
выпадает из поиска молча, без единой ошибки. Поэтому:

```bash
node scripts/set-domain.mjs sro-rostov.ru     # или https://sro-rostov.ru/
npm run build
```

Скрипт заодно убирает пометку TODO про домен и падает с ошибкой, если хоть
где-то `example.com` остался.

Сторожит всё набор `og-sitemap.mjs` (100 проверок): картинка отдаётся и ровно
1200×630, карта валидна и покрывает все страницы без дублей и лишнего, robots
её называет, а canonical каждой страницы указывает на неё саму и не совпадает
с соседней — копипаста здесь ничем другим не ловится.

## Микроразметка, страница 404 и иконка для iOS

**Микроразметка Schema.org.** Поисковик читает страницу как текст и не знает,
что «6164132279» — это ИНН, а «+7 900 133-02-19» — телефон компании, а не
случайное число. Разметка называет это прямо: по ней собирается карточка
организации в поиске и путь под ссылкой (хлебные крошки).

Пишется в статический HTML, а не выводится из React: Яндекс выполняет скрипты
не всегда, и разметка, появляющаяся только после запуска приложения, для него
может не существовать вовсе. Генератор `scripts/build-jsonld.mjs` берёт данные
из тех же файлов, что и сам сайт — `contacts.ts`, `facts.ts`, `regions.ts`
и заголовки страниц, — второго источника правды нет. На каждой странице
`Organization`, на десяти внутренних ещё и `BreadcrumbList`.

Тип `Organization`, а не `LocalBusiness`: последний означает место, куда
приходят клиенты, а сайт прямо говорит «дистанционно, личный визит не
требуется». Заявлять приём посетителей мы не будем. В `areaServed` те же
пятнадцать регионов, что в блоке «География работы».

**Страница 404** — `public/404.html`. Обычный статический файл без React
и без сборки: на неё уводит сам хостинг, когда адреса не существует, и она
обязана открыться, даже если скрипты сайта не загрузились. Поэтому шрифт
системный, а стили внутри файла — ни одной внешней зависимости. Контакты
в ней записаны отдельно от `contacts.ts`, и набор `jsonld-404.mjs` сверяет
их с подвалом сайта, чтобы при смене телефона они не разъехались.

**Иконка для iOS** — `public/apple-touch-icon.png`, 180×180. Safari не умеет
SVG-фавиконку для ярлыка «на экран Домой»: без PNG вместо знака компании там
окажется уменьшенный скриншот страницы. Рисуется из того же `favicon.svg`
скриптом `scripts/build-icons.mjs`, прозрачности нет намеренно — iOS
подкладывает под ярлык чёрный фон.

Сторожит всё набор `jsonld-404.mjs` (194 проверки). Главное, что он делает,
— сверяет разметку с тем, что реально отрисовано: имя, ИНН, телефон, почта
и улица из разметки обязаны находиться в подвале страницы, а название
последней крошки — совпадать с заголовком. Разметка, разошедшаяся с текстом,
хуже, чем её отсутствие, и глазом такое расхождение не видно.

## Приём заявок из квиза

Заявка уходит **на почту Игоря — `9001330219@mail.ru`**. Отправка с сайта —
`src/lib/lead.ts`, приёмник на сервере — `public/api/submit.php`.

Требование заказчика: форма обязана работать у посетителей из России **без
VPN и без задержек**. Это выполняет только контур со своим `submit.php`:
он лежит на том же домене, что и сайт, браузер посетителя никуда наружу не
ходит, а письмо уходит с хостинга напрямую на сервер mail.ru. Web3Forms —
зарубежный сервис и этому требованию не соответствует; он остаётся только
на время, пока сайт стоит на GitHub Pages, где PHP не выполняется.

| Где стоит сайт | Приёмник | Куда приходит |
| --- | --- | --- |
| Российский хостинг с PHP | `public/api/submit.php` | `9001330219@mail.ru` — вписано в `MAIL_TO` |
| GitHub Pages (сейчас) | Web3Forms | на почту, к которой привязан ключ `VITE_LEAD_ACCESS_KEY`. Нынешний ключ создан на тестовую почту `abayhanov2000@gmail.com`. Чтобы заявки шли Игорю уже с GitHub Pages, нужен новый ключ на web3forms.com, созданный на `9001330219@mail.ru`, — заменить в `.env` и в Secrets репозитория |

Если отправка не удалась (сервис не ответил за 10 секунд, отказал или
недоступен из России), посетитель видит экран «Не удалось отправить
заявку»: ответы не теряются, есть «Попробовать снова», «Отправить письмом»
(открывает почту посетителя с готовым текстом на `9001330219@mail.ru`),
WhatsApp с тем же текстом, Telegram, MAX и телефон. Письмо и мессенджеры от
сервиса приёма не зависят, поэтому заявка доходит и когда сервис закрыт.
Молчаливого «успеха» не бывает: если доставка не подтверждена, показывается
именно этот экран.

- В письме: тема `Заявка с сайта СРО — Имя, Телефон` (можно перезванивать
  прямо из списка писем), в теле — контакты и все ответы квиза.
- Кнопка «Ответить» в почте отвечает **клиенту**, а не сервису (поле `replyto`).
- Форма защищена honeypot-полем: заполнившему его боту показывается обычный
  экран успеха, но заявка не отправляется.

Сменить приёмник можно без правки кода — через переменные окружения
(см. `.env.example`). Формат запроса и ответа у своего обработчика намеренно
такой же, как у Web3Forms, поэтому фронтенд одинаков для обоих:

```
# Свой хостинг с PHP (токен уже вписан в submit.php, менять не нужно):
VITE_LEAD_ENDPOINT=/api/submit.php
VITE_LEAD_ACCESS_KEY=sro-mn3gi1r1iambpw0ljb25fzcdqwm1

# Web3Forms:
VITE_LEAD_ENDPOINT=https://api.web3forms.com/submit
VITE_LEAD_ACCESS_KEY=<ключ сервиса>
```

Без этих переменных используются значения по умолчанию из `src/lib/lead.ts`.
В GitHub Actions они пробрасываются из Secrets репозитория, если заданы.

### Свой обработчик: переезд на хостинг за пять шагов

Письмо уходит по SMTP **из ящика Игоря в его же ящик**: отправитель и
получатель совпадают, проверять SPF и DKIM почте не у кого, письмо приходит
за секунды и не попадает в спам. Заводить почту на домене сайта не нужно.

1. **Пароль для отправки.** В настройках ящика `9001330219@mail.ru` создать
   пароль для внешнего приложения (раздел в настройках так и называется;
   обычный пароль от почты для SMTP у mail.ru не работает). Скопировать его.
   Такой пароль даёт доступ только почтовым программам, и его можно отозвать
   одной кнопкой, не меняя основной.
2. **Заполнить `public/api/submit.php`** — блок настроек в начале файла:

   | Константа | Что вписать |
   | --- | --- |
   | `MAIL_TO` | уже вписано: `9001330219@mail.ru` |
   | `SMTP_HOST`, `SMTP_PORT` | уже вписаны: `smtp.mail.ru`, `465`. Сверить с тем, что показывает mail.ru в том же разделе настроек |
   | `SMTP_USER` | уже вписано: `9001330219@mail.ru` |
   | `SMTP_PASS` | пароль из шага 1 |
   | `FORM_TOKEN` | уже вписано: `sro-mn3gi1r1iambpw0ljb25fzcdqwm1`. Секретом не является — лежит в коде страницы, — только отсекает ботов |
   | `ALLOWED_HOST` | домен сайта. Вписывается сам командой `node scripts/set-domain.mjs вашдомен.ru` вместе с остальными адресами |

   `MAIL_FROM` остаётся пустым: при SMTP отправитель — сам `SMTP_USER`.
3. **Собрать сайт** с приёмником на своём домене:

   ```bash
   VITE_LEAD_ENDPOINT=/api/submit.php \
   VITE_LEAD_ACCESS_KEY=sro-mn3gi1r1iambpw0ljb25fzcdqwm1 \
   npm run build
   ```

   `public/api/submit.php` попадает в `dist/api/` сам.
4. **Залить содержимое `dist/`** в корень сайта на хостинге.
5. **Проверить** — открыть в браузере
   `https://вашдомен.ru/api/submit.php?selftest=sro-mn3gi1r1iambpw0ljb25fzcdqwm1`.
   Страница пришлёт проверочное письмо на `9001330219@mail.ru` и сообщит,
   ушло ли оно; если нет — что именно ответил сервер почты (неверный пароль,
   закрытый порт и т. п.). Без такой проверки о неверном пароле узнают от
   посетителя, который не дождался ответа.

Запасной способ — функция `mail()` хостинга: очистить `SMTP_USER` и вписать в
`MAIL_FROM` адрес **на домене сайта** (заводится в панели хостинга; с чужого
домена не сойдётся SPF, и письма уйдут в спам). Первое такое письмо почти
наверняка окажется в «Спаме» — нажать «Не спам» и добавить отправителя в
адресную книгу. При SMTP через собственный ящик этого не требуется.

Обработчик отсекает заголовочные инъекции, ограничивает частоту (10 заявок
с одного адреса в час), кодирует русскую тему по MIME, а тело письма — в
base64, чтобы проходило на любом сервере.

Проверка без почты — письмо записывается в файл:

```bash
SRO_MAIL_DRY_RUN=/tmp/lead.eml php -S 127.0.0.1:8000 -t dist
curl -X POST http://127.0.0.1:8000/api/submit.php \
  -H 'Content-Type: application/json' \
  -d '{"access_key":"sro-mn3gi1r1iambpw0ljb25fzcdqwm1","message":"проверка"}'
cat /tmp/lead.eml
```

Контур проверен целиком 08.09.2026 против тестового SMTP-сервера с TLS на
465 порту: приветствие, EHLO, AUTH LOGIN, конверт, DATA с base64-телом,
русская тема, `Reply-To` клиенту — письмо собирается правильно; неверный
пароль и закрытый порт `selftest` называет дословно. Проход квиза в
браузере → сборка с `VITE_LEAD_ENDPOINT=/api/submit.php` → PHP → письмо
проверялся 30.08.2026 (`SRO_MAIL_DRY_RUN`).

## Принципы контента

На сайте нет отзывов, выдуманных цифр, достижений, лицензий, цен и сроков —
только описание услуг и формата работы. Всё, что требует реальных данных,
вынесено в плейсхолдеры вида `[ИМЯ]`; пока плейсхолдер не заменён, блок с ним
не показывается, а не выводит скобки на экран.

Фотографий шесть. У пяти источник и лицензия подтверждены заказчиком; у шестой —
фона секции заявки — файл прислан заказчиком напрямую, а источник он пока не
назвал, и в учёте так и написано. Всё — в `public/img/CREDITS.md`. Логотипы СРО, НОСТРОЙ, НОПРИЗ, Минстроя, гербы и
флаги не ставятся: чужие обозначения плюс намёк на аккредитацию, которой нет.

Обещаний результата и сроков («вступление за 1 день», «гарантия внесения в
реестр», «ответ за 24 часа») на сайте нет и быть не должно: это не зависит от
исполнителя.

Единственное прямое обязательство — бесплатная консультация: она бесплатна
всегда, а не только в первый разговор. Это условие задал заказчик, в исходном
ТЗ его не было. Сказано оно в пяти местах — герой, «Стоимость» (подзаголовок
и карточка формата), FAQ, квиз, подвал; формулировки разные, смысл один.
Дословная оговорка «и первая, и все следующие» есть ровно одна, в подвале:
она переехала туда из убранной секции «Контакты». Меняете условие — правьте
все пять, иначе сайт начнёт противоречить сам себе.

## Ссылки мессенджеров и открытие приложения

Ссылки WhatsApp, Telegram и MAX открываются **в той же вкладке** — без
`target="_blank"`. Это не упущение, а условие работы: ни iOS, ни Chrome на
Android не запускают universal link / app link, если переход идёт в новую
вкладку. С `target="_blank"` нажатие на телефоне открывало пустую страницу
или веб-версию вместо приложения — заказчик поймал это на живом сайте.

Размен осознанный: на компьютере посетитель уходит на веб-версию мессенджера
и возвращается кнопкой «Назад». Цель лендинга — чтобы человек написал, а
телефонов среди посетителей заведомо больше. Телефон и почта всегда работали
так же, без новой вкладки.

Сторожит это `deeplinks.mjs`: проверяет, что ни на одной ссылке мессенджера
нет `target="_blank"` и что схема у всех `https` (у `tg://` нет universal
link — у кого нет приложения, увидит ошибку браузера). Проверено обратным
контролем: с возвращённым `target="_blank"` набор падает.

Мессенджеры на странице помечены атрибутом `data-channel` — раньше проверки
опознавали их как раз по `target="_blank"`, и признак пришлось заменить на
такой, который не завязан на поведение ссылки.

Две вещи, которые кодом не чинятся, если чат всё-таки не открывается:

- **Telegram.** Ссылка стоит на @username (`t.me/Igor_bgspb`), а не на номер.
  Форма `t.me/+<номер>` тоже рабочая, но открывает чат лишь у тех, кому
  владелец номера разрешил находить себя по телефону; у остальных приложение
  открывалось без чата. Заказчик поймал это вживую — с именем пользователя
  условия нет.
- **WhatsApp заблокирован в России.** Роскомнадзор исключил домены
  `whatsapp.com` и `web.whatsapp.com` из национальной системы доменных имён
  в феврале 2026 года; доступ то появляется, то пропадает, устойчиво работает
  только через VPN. Ссылка на сайте корректна, но у посетителя из России
  канал может не сработать — и это не чинится кодом. Решение, оставлять ли
  WhatsApp на сайте, за заказчиком; рабочие каналы для российской аудитории —
  Telegram, MAX и телефон.
- **Встроенный браузер мессенджера.** Если сайт открыт изнутри Telegram или
  VK, их встроенный браузер обрабатывает ссылки по-своему. Проверять нужно
  в обычном Chrome или Safari.

## Страницы видов СРО

Кроме главной у сайта три отдельные страницы — по одной на вид СРО:

| Адрес | О чём |
|---|---|
| `/sro-stroiteley/` | вступление в СРО строителей |
| `/sro-proektirovshchikov/` | вступление в СРО проектировщиков |
| `/sro-izyskateley/` | вступление в СРО изыскателей |

Попасть на них можно с главной: карточка вида СРО целиком кликается и ведёт
на свою страницу, кнопка «Подробнее» при наведении заливается фирменным цветом.

**Не одностраничник с роутером, а четыре обычных html.** Каждая страница —
своя точка входа Vite (`vite.config.ts`, `build.rollupOptions.input`). Так у
неё настоящий адрес: ссылку можно прислать, поисковик видит три отдельные
страницы, а хостингу не нужен фолбэк на `index.html`, без которого адрес,
открытый напрямую, отдавал бы 404.

**Что на страницах.** Кому обязательно членство, область деятельности, обе
таблицы взносов в компенсационные фонды, требования к специалистам, срок
рассмотрения заявления и — только у строителей — региональный принцип.
Содержимое лежит в `src/content/sroDetails.ts`.

**Ни одной цифры «на глаз».** Каждая величина на страницах — из закона, и
рядом с ней стоит статья, по которой её можно проверить. Суммы взносов —
это установленные законом МИНИМУМЫ: конкретная СРО не вправе взять меньше,
но своими документами может установить больше, и на странице это сказано
прямо. Про цены и сроки нашей работы там нет ни слова — таких данных
заказчик не давал.

**Глубина вложенности.** Пути к картинкам из `public/` и ссылки на секции
главной написаны руками, и на странице в подпапке они ломаются молча:
`./img/x.webp` превращается в `/sro-stroiteley/img/x.webp`, а `#services`
ведёт в никуда. Поэтому оба вида ссылок проходят через `src/lib/site.ts`, а
точка входа объявляет свою глубину один раз — `setSiteRoot('../')`. Сторожит
это набор `pages.mjs`: он открывает каждую страницу и требует, чтобы
картинки реально загрузились, а ссылки реально отвечали 200.

**Возврат в квиз.** Кнопка на странице ведёт на главную с уже выбранным
видом: `/?sro=construction#quiz`. Квиз читает параметр при старте и не
спрашивает про вид второй раз — человек уже ответил, открыв страницу.
Якорь при этом отрабатывает не сам: браузер прыгает к нему сразу после
разбора HTML, а разметку рисует React, и в этот момент секции ещё нет.
Прокрутку после отрисовки делает `src/lib/useHashScroll.ts`.

## Проверка цифр 04.09.2026 и почему таблиц взносов нет

Все нормы на страницах видов СРО прошли состязательную проверку: восемнадцать
утверждений, у каждого три независимых проверяющих с прямой задачей
**опровергнуть**, а не согласиться. Что она изменила:

| Было | Стало | Почему |
|---|---|---|
| изыскания — ч. 4 ст. 47 | **ч. 2 ст. 47** | ч. 4 к членству в СРО не относится |
| строители — ч. 2.1 ст. 52 как «обязанность» | **ч. 2 ст. 52** — обязанность, **ч. 2.1** — случай, когда членство НЕ нужно | порог сам по себе ничего не решает: сначала важно, с кем заключён договор |
| срок — ч. 5 ст. 55.6 | **ст. 55.6** без части | проверяющие разошлись: часть 4 или 5 |
| взносы — ч. 10–13 ст. 55.16 | **ст. 55.16** без части | порядок частей не подтверждён |
| снос — ст. 55.31 как «норма о сносе» | снос назван в области деятельности | ст. 55.31 — требования к сносу, а обязанность членства идёт из ст. 52 |
| «участвуете в 44-ФЗ и 223-ФЗ» | «**намерены** заключать договоры конкурентными способами» | взнос в КФ ОДО привязан к заявленному намерению, а не к факту участия |

**Правило, которое из этого следует: номер части статьи ставим только там, где
на нём сошлись все проверяющие.** Неверный номер части выглядит точнее, чем
есть, и подрывает доверие ко всей странице.

### Таблицы взносов: сняты и возвращены в тот же день

Проверка оставила два возражения:

1. **Первый уровень для строителей.** Три проверяющих с высокой уверенностью
   называют 60 млн ₽, а не 90 млн ₽. Значение 90 млн взято из уже сверенных
   данных соседнего проекта (`norma-site/src/config/facts.ts`) со ссылкой на
   435-ФЗ от 04.08.2023.
2. **Порядок частей ст. 55.16** — где строители, а где проектировщики.

Проверить по первоисточнику отсюда нельзя: правовые сайты закрыты сетевой
политикой — `consultant.ru`, `pravo.gov.ru`, `garant`, `cntd`, `sudact` дают
403 на CONNECT. Поэтому таблицы со страниц сняли: цифра, по которой человек
переводит деньги, не может стоять «примерно».

**В тот же день спор разрешился.** Заказчик прислал сохранённые страницы
работающего сайта конкурента по всем трём видам СРО. Все четыре таблицы там
совпали с нашими до рубля, включая спорный первый уровень 90 млн ₽. Итого
за 90 млн: наши данные, уже сверенные данные соседнего проекта и три живые
коммерческие страницы. Против — только память трёх проверяющих. Таблицы
возвращены, `FUNDS_CONFIRMED = true`.

Чего это не отменяет: сайт конкурента подтверждает, что так считает рынок,
но он не первоисточник. Перед выходом на боевой домен таблицы стоит сверить
с действующей редакцией ст. 55.16 ГрК РФ.

**Номера частей ст. 55.16 не проставлены и не будут** — проверяющие в них
разошлись, а страницами конкурента их не подтвердить: он частей не указывает
вовсе. Проверка `pages.mjs` отдельно следит, чтобы они не появились.

## Вычитка 06.09.2026

По просьбе заказчика все одиннадцать страниц вычитаны целиком: текст снят
с собранного сайта (`scratchpad/pwtest/dump-text.mjs` собирает видимый текст
и мета-описания в один файл), прогнан через формальные проверки (двойные
пробелы, дефис вместо тире, машинные кавычки, скобки-плейсхолдеры, повтор
слова, ё/е, латиница внутри кириллицы) и прочитан глазами. Формальные проверки
ничего не нашли; глазами нашлось семь мест, все исправлены:

- описание главной для поиска и Open Graph обещало «все регионы России» и
  повторяло старый заголовок первого экрана — при списке из пятнадцати
  регионов это неправда; теперь «работа дистанционно»;
- описание страницы изыскателей ссылалось на ч. 4 ст. 47 ГрК РФ, тогда как
  на самой странице после проверки стоит ч. 2 ст. 47 (ч. 4 к членству не
  относится) — в описании и в `sroDetails.ts`;
- описание страницы строителей называло ч. 2.1 ст. 52 нормой об обязанности
  членства, хотя это порог в 10 млн ₽; обязанность — ч. 2. Теперь «ч. 2 и 2.1»;
- страница «Подбор и проверка СРО» утверждала, что взносы в фонды «одинаковы
  для всех СРО одного вида», а страницы видов рядом говорят, что СРО вправе
  установить больше минимума. Противоречие снято: одинаков минимум;
- шаг «Оплата взносов»: вступительный взнос был вынесен в хвост перечисления
  через «и», читалось как часть условия про закупки — порядок переставлен;
- подзаголовок квиза «4 вопроса меньше чем за минуту» — без тире; подпись

## Тон текстов: деловой, без острот

05.09.2026 заказчик заметил, что тексты «выглядят так, будто сделала
моделька». Претензия справедливая, и дело не в фактах — они не менялись, —
а в регистре: короткие рубленые фразы через тире, афоризмы («не лазейка,
а риск»), заголовки-крючки («это ещё не отказ»), авторские ремарки
(«честно о том, чего делать нельзя», «обещать за СРО я не могу»). Так пишут
колонки, а не сайты компаний.

Правило с этого дня: **деловой ровный тон, как в описании услуги.** Полные
предложения, факт → что делаю. Заголовок называет предмет («Специалисты
НРС: требование закона и варианты решения»), а не интригует. Ремарок от
первого лица про собственную честность нет: честность показывают ссылки на
статьи и оговорки о том, чего закон не допускает, а не слова о ней.
Первое лицо в действиях («подготовлю», «проверю») остаётся — это по-прежнему
речь специалиста компании; в блоке «О нас» компания названа по имени,
а специалист — в третьем лице.

Переписаны: первый экран, «Типовые ситуации», «Услуги», «Виды СРО»,
«Специалисты НРС» (целиком), «Стоимость», «О нас», FAQ, «География работы»,
подвал, шаги и оговорки на страницах видов (`STEPS` и `who` в
`sroDetails.ts`, пояснения к фондам и срокам в `DetailPage.tsx`).
Формулировка заказчика «Консультация бесплатная — и первая, и все следующие»
в подвале не тронута: это его условие, сказанное его словами.

Заголовок первого экрана — «Вступление в СРО под ключ», подзаголовок называет
три вида организаций. Более длинные варианты («…строителей, проектировщиков
и изыскателей») на 1440px разбивались на четыре строки и сталкивали карточки
видов ниже первого экрана — это ловит проверка T7 в `t567.mjs`. По той же
причине подзаголовок «Видов СРО» держится в две строки.

**Реквизиты — в подвале.** Из карточки «О нас» ИНН, КПП и адрес переехали
в подвал, в колонку под именем компании: там их ищут по привычке, и там они
стоят рядом с юридическим именем в копирайте. Карточка «О нас» стала
визиткой: знак, имя, город, условия работы и ссылка на реквизиты.
Пункт «География работы» в меню «Услуги» подписан «15 регионов, от
Санкт-Петербурга до Якутска» — число из списка заказчика.

## Шапка: выпадающие меню

В шапке два раскрывающихся пункта — «Виды СРО» и «Услуги» — и три обычных:
«Стоимость», «О нас», «FAQ». Навигация целиком лежит в `src/content/nav.ts`
(`MENU`): её перечисляют шапка, мобильное меню и подвал, и расходиться эти
списки не должны. Ссылки двух видов: якорь секции главной (`kind: 'anchor'`)
и папка страницы вида СРО (`kind: 'page'`); адрес собирает `navHref()`, чтобы
со страницы вида якорь получил `../`, а страница — полный путь.

**Пункт меню — название с подсказкой, а не голое слово.** Человек ещё не
знает, «строители» он или «проектировщики», и три названия подряд ему не
помогают. Подсказка под видом — слова из области деятельности на его странице
(у изыскателей пять пунктов на «инженерно-…» не перечисляются целиком: в меню
они занимали четыре строки). Набор `header.mjs` сверяет, что каждое слово
подсказки есть на странице вида — подсказка не может уйти от того, что там
написано. У «Услуг» подсказки ведут по секциям главной: вступление и
сопровождение, специалисты НРС, документы, регионы.

**Три способа ввода — три разных поломки, поэтому логика такая:**

- мышь: открывает наведением, закрывает уходом курсора с задержкой 120 мс;
  между кнопкой и карточкой «мостик» `pt-3`, иначе курсор по дороге к пункту
  выходил за кнопку и меню схлопывалось под рукой. Щелчок по открытому меню
  его не закрывает: намерение щелчка — «открой», а не «переключи»;
- касание (планшет шире 1024px): наведение не считается вовсе — касание
  порождает синтетический mouseenter, меню открывалось от него, а следующий
  click тут же закрывал. Тап переключает, тап мимо закрывает (слушаем
  `pointerdown` на документе: iOS не переводит фокус на кнопку при касании,
  и на `onBlur` там рассчитывать нельзя);
- клавиатура: фокус сам по себе не открывает (иначе на Android тап открывал
  бы фокусом и закрывал щелчком), Enter и пробел переключают, Tab идёт по
  пунктам, уход фокуса и Escape закрывают. Закрытая карточка — `invisible`,
  а не `display: none`: анимация появления остаётся, а ссылки внутри Tab
  всё равно пропускает.

На странице вида его пункт помечен `aria-current="page"` и подсвечен. В
мобильном меню группы не сворачиваются: два лишних тапа ради трёх строк —
плохой размен; заголовок группы набран подписью, пункты под ним с подсказками.

Ширина: на 1024–1279px пять пунктов с двумя стрелками умещаются с `gap-5`,
с 1280 — `gap-7`; телефон на этих ширинах по-прежнему иконкой. `header.mjs`
проверяет на 1024, 1280 и 1440, что шапка стоит в одну строку.

## Специалисты НРС: ответ на самый частый стопор

Блок `#nrs` стоит сразу за «Документами» — там о специалистах впервые заходит
речь, там же у человека возникает «а у меня их нет». Ответ должен стоять рядом
с вопросом, а не в FAQ внизу страницы.

**Почему отдельная секция, а не строчка в услугах.** В «Услугах» НРС и НОК
стоят карточками «помогу с тем-то» — это ответ на вопрос «что вы делаете».
Вопрос у посетителя другой: «мне вообще можно?». В FAQ ответ был, но короткий
— «разберём вашу ситуацию и обсудим законные варианты», после чего человек
уходил ровно с тем же непониманием, с каким пришёл.

**Порядок внутри блока: сначала норма, потом варианты.** Иначе получается
разговор о способах обойти требование, а требование настоящее: не менее двух
специалистов, сведения о которых включены в национальный реестр, по основному
месту работы (ст. 55.5-1, ст. 55.6 ГрК РФ). Дальше три пути — посмотреть своих,
внести своего в реестр, взять специалиста со стороны.

**Оговорка «чего я делать не буду» — половина смысла блока.** «Аренда»
специалиста и фиктивное трудоустройство — первое, что предлагают посредники;
честнее сказать об этом самому. Там же названы два риска: соответствие
требованиям проверяют не только на входе, и свидетельство о независимой оценке
квалификации действует ограниченное время — истекло, специалист выбывает из
реестра, компания перестаёт соответствовать требованию о двух специалистах.

**Чего в блоке намеренно нет.** Обучения и страхования гражданской
ответственности: в списке услуг заказчика их нет, а подтверждения, что он их
оказывает, у меня тоже нет. Придумывать услугу нельзя — это то же самое, что
придумать цифру. Появится подтверждение — впишем.

Из FAQ на блок ведёт ссылка, в навигации подвала он назван «Специалисты НРС»
(`SECTIONS` в `src/content/nav.ts`; в шапку не поставлен — там помещается
ровно четыре пункта). Сторожит блок набор `nrs.mjs`: норма со ссылкой на
статью, три пути, оговорка, отсутствие плейсхолдеров, живая ссылка из FAQ.

## География: карта охвата

Последний блок перед подвалом — карта России, где закрашены регионы работы,
и список под ней. Список от заказчика, лежит в `src/content/regions.ts`;
контуры — в `src/content/mapData.ts`, он сгенерирован.

**Почему карта И список, а не что-то одно.** Карта одним взглядом показывает
главное: работа идёт от Петербурга до Якутска. Но на телефоне карта России
шириной 360 пикселей превращает Кострому в пиксель — ни прочитать, ни попасть
пальцем. Поэтому рабочая часть всегда список, а карта показывает охват.
Карта идёт во всю ширину, список — под ней: в две колонки рядом карта
ужималась до трети экрана, а ради неё блок и делался.

**Связь в обе стороны.** Наводите на строку — загорается регион; наводите на
регион — подсвечивается строка. Москва и Московская область — одно пятно,
Петербург с Ленинградской областью тоже, поэтому у пятнадцати строк
тринадцать пятен, и общее пятно подсвечивает обе свои строки. На телефоне
наведения нет, поэтому по региону работает и тап.

**Границы настоящие.** Раньше контур был нарисован от руки по опорным точкам:
узнаваемый силуэт, но показать на нём регион было нечем — только булавка.
Разница не косметическая: закрашенная Якутия сразу показывает масштаб работы,
точка на её месте говорила ровно столько же, сколько точка на Костроме.

Источник границ — [click_that_hood](https://github.com/codeforamerica/click_that_hood)
(Code for America, лицензия MIT), файл `public/data/russia.geojson`: 83 субъекта
с русскими названиями. Крыма в этом наборе нет — данные 2013 года, — его контур
остался прежним, по опорным точкам; они в генераторе. Источник и лицензия
записаны в `public/img/CREDITS.md` по тому же правилу, что и фотографии.

Проекция — равновеликая коническая Альберса (стандартные параллели 52° и 64°,
осевой меридиан 100° в. д.). Она даёт узнаваемую «арку» России, где Калининград
и Чукотка опускаются к краям; линейная проекция по широте и долготе, которая
была здесь раньше, растягивала север и делала страну плоской лентой.

**Генератор — `scripts/build-map.py`.** Файл границ в репозитории не хранится,
скрипт берёт его аргументом:

```bash
curl -sSL -o /tmp/russia.geojson \
  https://raw.githubusercontent.com/codeforamerica/click_that_hood/master/public/data/russia.geojson
python3 scripts/build-map.py /tmp/russia.geojson > src/content/mapData.ts
```

Внутри: проекция, упрощение Дугласа–Пейкера (порог 1,1 пикселя итоговой
карты) и выброс колец мельче 3,5 пикселей — иначе арктические острова дают
крошку, которую всё равно не видно, а весят они как половина Якутии.
Реализация упрощения не рекурсивная намеренно: у Якутии кольца на десятки
тысяч точек, рекурсия упирается в лимит стека.

**Карта грузится отдельным файлом.** Контуры 83 субъектов — 24 КБ после
сжатия, больше половины скрипта главной страницы. Блок стоит перед подвалом,
до него ещё надо долистать, поэтому `mapData.ts` подключается динамическим
`import()` после первой отрисовки: на скорость открытия сайта карта не влияет.
Место под неё держится заранее (`aspect-ratio`), чтобы страница не дёргалась,
когда файл придёт.

Правило заливки — `evenodd`, и это не украшательство: Адыгея лежит внутри
Краснодарского края, Ненецкий округ — внутри Архангельской области. Без
`evenodd` эти дырки залились бы, и анклав пропал бы с карты.

При наведении рядом с городом всплывает подпись региона. Ширина плашки
считается по числу букв — измерить текст в SVG нечем; для одного-двух слов
этого хватает. Плашка прижимается к краям карты и уходит под метку у верхней
кромки: у Крыма и Якутска она иначе обрезалась краем.

Сторожит блок набор `regions.mjs`: полнота списка, наличие контуров, связь
строки с регионом и отсутствие горизонтального скролла на 390px.

## Имя на сайте: компания, не человек

Сайт делался как страница частного специалиста и написан от первого лица.
03.09.2026 заказчик попросил убрать ФИО специалиста и представить компанию из
реквизитов — ООО «БИЗНЕС-ГРУПП». Сделано так:

- компания везде названа одинаково: **ООО «БИЗНЕС-ГРУПП»** (`CONTACTS.brand`),
  подпись под именем — «Вступление в СРО» (`CONTACTS.role`). Это шапка, подвал,
  `<title>`, описание и Open Graph;
- рядом с именем стоит ИНН там, где он к месту: в копирайте подвала и в
  карточке «Реквизиты» полным набором (ИНН, КПП, адрес), в политике и согласии
  — в определении Оператора (`REQUISITES` в `facts.ts`);
- ФИО на странице нет нигде, включая `<title>` и Open Graph;
- фраза «Меня зовут …» из блока «О специалисте» убрана, остальной текст
  первого лица оставлен: он читается как речь специалиста компании и держит
  главное обещание сайта — «работаете с одним человеком, а не с отделом
  продаж». В FAQ «частный специалист» заменён на «один специалист».

Сначала короткий бренд «Бизнес-Групп» стоял в шапке и подвале, а полное имя —
только в копирайте и документах. 03.09.2026 заказчик попросил единое написание:
разнобой читается посетителем как два разных лица, а имя из реестра — то, по
чему компанию проверяют. Длиннее короткого бренда на 6 символов, но помещается
в одну строку и на 1440, и на 360 — проверено на странице. Правило сторожит
набор проверок `naming.mjs`: он сверяет шапку, подвал, `<title>`, Open Graph
и описание, требует ИНН в подвале и запрещает короткое написание без «ООО»
и незаполненные реквизиты в квадратных скобках на экране.

Переводить весь текст на «мы» не стали: это 42 строки в 12 компонентах и
смена характера сайта, а не правка. Если заказчик решит, что компании нужно
«мы», — это отдельная задача.

Банковские реквизиты (счёт, БИК, корр. счёт) в репозиторий не внесены: они
для счетов и договоров, сайту не нужны.

## Первый экран: кадр вместо портрета

Заказчик попросил первый экран «красивее и профессиональнее», но портрет
специалиста публиковать не будет. Экран двухколонный: текст слева, справа его
же фотография рабочего стола (каска, уровень, планы) в фирменном дуотоне на
подложке фирменного цвета со сдвигом — она даёт глубину вместо тени, которая
на светлом фоне читалась бы грязью.

Заголовок в колонке уже, чем был по центру, поэтому на `lg` его кегль 2.9rem
вместо 3.4rem — иначе ломался на пять строк.

Сначала этот же кадр стоял и фоном под квизом — как рамка страницы. Заказчик
заметил повтор; замена архивной синькой ему не понравилась. Сейчас под квизом
кадра нет: чистая тёмная заливка с двумя мягкими пятнами фирменного цвета.
Новый кадр заказчик присылает через репозиторий — скачать из интернета из этой
среды нельзя, фотостоки закрыты сетевой политикой (проверены pexels, unsplash,
pixabay, wikimedia, freepik). Как появится: `<picture>` на `opacity-50` плюс
плёнка `bg-accent-950/65`, контраст надписей перемерить (см. «Фон секции
заявки» ниже).

## Цвет

Акцент — кобальтовый синий (`accent` в `tailwind.config.js`), единственный
акцентный цвет сайта. Нейтральная шкала переопределена на тёплую: на чистом
сером холодный акцент и синие фотографии давали ощущение мороза. Это greige —
серый со сдвигом в жёлтый, а не бежевый, поэтому деловой вид сохраняется.

Фотографии подчиняются тому же правилу: тёмная точка дуотона — фирменный синий,
светлая — кремовая (см. `public/img/CREDITS.md`). Меняете одно — проверяйте
второе, иначе интерфейс и снимки разойдутся по температуре.

Фон секции заявки — фотография (каска «СРО», кодексы, чертежи), и она идёт
с затемняющей плёнкой поверх (`bg-accent-950/65` под кадром на `opacity-50`).
Плёнка не украшение: светлые места снимка поднимают яркость подложки под
белым заголовком и надписью «Заявка», а последняя — самая уязвимая, у неё
контраст ниже всех. Мерить надо по каждой надписи её собственным цветом, а не
по одному белому заголовку: у заголовка запас всегда большой, и замер по нему
разрешает то, что «Заявке» уже вредит. Замерено: без фото 8,56:1, с фото
и плёнкой 5,88:1 на десктопе и 6,07:1 на телефоне при норме 4,5; без плёнки
уходит ниже нормы. Меняете кадр — перемеряйте обе величины разом. Рисованный
вариант сцены со столом лежит в `assets-src/desk-drawing.svg`; рисунку плёнка,
наоборот, противопоказана — она съедает светлые линии.

Анимации лёгкие (fade/reveal/hover) и отключаются при `prefers-reduced-motion`.
Карточка приподнимается под курсором только если она кликается целиком:
подъём — это обещание клика (`src/components/ui/card.ts`).
