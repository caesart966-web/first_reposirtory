# YDS DENEME — генератор пробных китов

Собирает пробный буклет YDS (экзамен по английскому в Турции) в виде `.docx`,
свёрстанного как настоящая брошюра ÖSYM: две колонки, вопрос в рамке, основа
полужирным, варианты A–E, турецкие заголовки разделов, колонтитулы.

Один кит — 54 вопроса с номерами 27–80. Готовые киты лежат в `dist/`.

```
yds-kit/
├── README.md                     ← этот файл
├── spec.md                       ← правила кита: уровни, раскладка, типы ловушек
├── build_kit.py                  ← проверка правил + вёрстка .docx
├── check_output.py               ← проверка, что в буклете напечаталось всё
├── kits/
│   ├── kit-01.json               ← содержание кита 1 (вопросы, ответы, словарь)
│   ├── kit-02.json               ← кит 2
│   └── kit-03.json               ← кит 3
└── dist/
    ├── YDS-DENEME-Kit-01.docx    ← готовые буклеты
    ├── YDS-DENEME-Kit-02.docx
    └── YDS-DENEME-Kit-03.docx
```

Сейчас сделаны киты 1–3 — все три уровня **B2 Beginner** (см. таблицу уровней
в `spec.md`). Темы текстов и диалогов во всех трёх разные.

## Как собрать

```bash
pip install python-docx
cd yds-kit
python3 build_kit.py kits/kit-01.json
```

В ответ печатается сводка — по ней сразу видно, что кит собран правильно:

```
Kit 1 / 12 — Level: B2 Beginner
  sorular : 54 (27-80)
  seviye  : B2 (48 soru) / C1 (6 soru)
  kelime  : 84 madde
  cevaplar: 27-C 28-A 29-E 30-B 31-E 32-D 33-C 34-A ...
  çıktı   : dist/YDS-DENEME-Kit-01.docx
```

Если правило нарушено, файл **не собирается** — вместо буклета печатается список
нарушений. Проверяются: число и нумерация вопросов, соответствие разделам,
наличие пяти вариантов, того, что верный и «ловушечный» варианты существуют и
не совпадают, наличие всех четырёх типов вопросов у каждого текста
(`according to` / `it is clear` / вывод / главная мысль), объяснение к каждому
вопросу, минимум 40 слов в словаре и то, что каждое слово из словаря
действительно встречается в тесте.

## Как проверить, что в буклете напечаталось всё

Первая проверка смотрит на JSON. Вторая смотрит на **готовый .docx**: собирает
из него PDF и ищет в тексте каждый вопрос, каждый вариант, каждое объяснение,
каждое слово словаря и каждую букву в ответнике.

```bash
python3 check_output.py kits/kit-01.json
```

Это не перестраховка. Пока рамки вопросов были помечены как неразрывные
(`w:cantSplit`), LibreOffice не переносил не влезающий вопрос в следующую
колонку, а **обрезал** его: в ките 3 у вопроса 72 в буклете не было вариантов
B–E. В JSON при этом всё было на месте, и первая проверка молчала.

Прогоняйте обе проверки после каждой правки вёрстки.

## Как сделать следующий кит

Скопируйте `kits/kit-01.json` в `kits/kit-02.json`, поменяйте `kit` на 2 и
напишите новое содержание. Уровень подставится сам: 1–3 — B2 Beginner,
4–7 — B2 Advanced, 8–12 — C1 Entry (см. `spec.md`).

Один вопрос выглядит так:

```json
{
  "no": 27, "group": "sentence_completion", "level": "B2",
  "stem": "Because the new wing of the museum was designed ..., ----.",
  "options": { "o1": "верный вариант", "o2": "...", "o3": "...", "o4": "...", "o5": "..." },
  "order": ["o2", "o3", "o1", "o4", "o5"],
  "answer": "o1",
  "trap": "o3",
  "why": "почему верный вариант верен — одна фраза по-турецки",
  "trap_note": "в чём ловушка самого популярного неверного варианта"
}
```

Ключевая деталь: **буквы A–E нигде не пишутся руками.** Вы задаёте порядок
вариантов в `order`, а какая буква досталась верному ответу, вычисляется при
сборке — и попадает разом в вопрос, в cevap anahtarı и в açıklamalar. Разъехаться
они не могут. Чтобы ответы распределялись по буквам ровно, двигайте `order`, а не
переписывайте текст.

Особые случаи:

- **Тексты 43–62** — в массиве `passages`, по одному на четыре вопроса
  (`"first": 43, "last": 46`). Печатаются во всю ширину над своими вопросами.
- **Диалоги 63–67** — вместо `stem` массив `dialogue`: пары «кто говорит» —
  «реплика», пропущенная реплика пишется как `----`.
- **Вопросы 76–80** — вместо `stem` массив `sentences` из пяти предложений;
  `answer` и `trap` — римские цифры (`"IV"`), варианты A–E подставляются сами.

## Что печатается в конце кита

1. **SORU AÇIKLAMALARI** — по каждому вопросу: почему верный ответ верен и какая
   ловушка в самом заманчивом неверном варианте (с указанием его буквы).
2. **CEVAP ANAHTARI** — сетка «Soru | Doğru | Benim cevabım | ✓/✗»; колонка
   «Benim cevabım» пустая, её заполняет решающий. Ниже — сплошной список
   `27-C 28-A ...` до 80.
3. **KELİME RÖNTGENİ** — все C1+ слова и устойчивые выражения теста, две колонки
   «английское — турецкое», по алфавиту, без примеров.

## Чего в буклете нет и не должно быть

- Логотипа и любых обозначений ÖSYM: это учебное **deneme**, а не официальный
  бланк. На обложке это сказано прямо (правило 6 в «SINAVDA UYULACAK KURALLAR»).
- Вопросов, переписанных из настоящего экзамена. Стиль, типы ловушек и вёрстка
  взяты с реального буклета 2025-YDS/3, тексты и вопросы написаны заново.

## Мелочи вёрстки, которые легко сломать

- Вопрос не должен разрываться между колонками — за это отвечает цепочка
  `keep with next` у абзацев внутри рамки (`hold_together()`). Не заменяйте её
  на `w:cantSplit` у строки таблицы: Word так и делает, но LibreOffice режет
  не влезающий вопрос и часть вариантов пропадает из буклета.
- Порядок элементов в WordprocessingML жёсткий: `_insert_ordered()` ставит
  `tblW`, `tblBorders`, `pBdr` и прочее на положенное место. Если добавлять их
  простым `append`, Word и LibreOffice перестанут открывать файл вообще.
- Колонтитулы собраны таблицей без рамок, а не табуляциями: у табуляций
  выравнивание зависит от табстопов шаблона и «ENGLISH» уезжает к центру.
- В сплошном списке ответов стоит неразрывный дефис (U+2011), иначе «44-D»
  переносится на две строки.

- Рамка-инструкция («27-36: For these questions…») печатается внутри колонки,
  как в настоящем буклете. Если вынести её в одноколоночную секцию, она
  оторвётся от первого вопроса и повиснет внизу страницы.
